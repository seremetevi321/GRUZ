# Безопасная сделка для грузоперевозок — MVP

Банк держит деньги заказчика в резерве (цена + 10% на простой и неустойки) и выплачивает их перевозчику автоматически, когда документы и трек подтверждают рейс. Система сверяет документы между собой, находит место ошибки, называет виновника и считает компенсацию. Каждое решение записывается в ленту простым языком.

## Запуск

### 1. Сервер и база — одной командой

Нужен Docker Desktop.

```bash
docker compose up --build
```

Сервер стартует на `http://127.0.0.1:8000` с тестовыми данными из ТЗ. Тот же адрес в браузере открывает интерфейс: так можно показывать в трёх окнах браузера, если десктоп не нужен.

### 2. Десктоп-приложение (macOS)

Один раз поставить инструменты: Xcode Command Line Tools (`xcode-select --install`), Rust (`curl https://sh.rustup.rs -sSf | sh`), Node.js 20+.

```bash
cd frontend
npm install
npm run tauri dev        # запуск для разработки
npm run tauri build      # сборка SafeDeal.app и .dmg в src-tauri/target/release/bundle/
```

Приложение открывает сразу три окна: заказчик, перевозчик, оператор. Логин в каждом подставлен, остаётся ввести пароль.

## Сценарий показа

| № | Что делать | Что увидит жюри |
|---|---|---|
| 1 | Заказчик: «Новая заявка», 120 000 → «Создать» → «Зарезервировать». Перевозчик: «Принять» → «Весь трек разом» → «Предложить стоимость». Заказчик: «Подтвердить и выплатить». | К резервированию 132 000 ₽, плашка «Оплата гарантирована», выплата 120 000 ₽, возврат 12 000 ₽ |
| 2 | Цена 85 000. В симуляторе «Погрузка, мин» = 270, дальше как в п. 1. | Расчёт «150 мин × 1 000 ₽/ч = 2 500 ₽», выплата 87 500 ₽, возврат 6 000 ₽ |
| 3 | В симуляторе нажать «другой водитель», дальше как в п. 1. Затем «вернуть водителя из ТТН» → «Подать исправленный путевой лист». | Блокировка с обоими именами и подсвеченным полем, после исправления — выплата |
| 4 | Цена 90 000. Перевозчик предлагает 95 000, заказчик пишет причину и жмёт «Оспорить». Оператор открывает заявку из «Требуют внимания», ставит 92 000 и комментарий. | Деньги в резерве до решения, выплата 92 000 ₽, возврат 7 000 ₽ |
| 5 | Новая заявка; в симуляторе указать номер ТТН из заявки сценария 1 и нажать «Подписать накладную». | Заявка отклонена, флаг «дубль», первая не затронута |
| 6 | Окно оператора → «Панель». | Метрики совпадают с только что показанным, «Баланс сходится» |
| — | Оператор: «Сбросить данные» (два нажатия). | Исходное состояние, окна не разлогиниваются |

**Что имитируется:** ЭДО (накладная), электронные путевые листы, телематика (трек) — кнопками симулятора; счета банка — учётными счетами в базе; подписи документов.
**Как подключается в пилоте:** симулятор заменяется адаптерами, которые шлют те же события в тот же API (`POST /api/orders/{id}/events`, идемпотентно по `event_id`); учётные счета — проводками в АБС; демо-режим (`DEMO_MODE=0`) выключает симулятор и сброс.

## Анализ документов (модуль 2)

Перевозчик загружает фото, скан или PDF накладной либо путевого листа. Система сама определяет тип документа, заполняет цифровую форму и показывает, откуда на изображении взято каждое значение. Поля, в которых она не уверена, подсвечены «проверьте». Перевозчик исправляет, что нужно, и подаёт документ. Дальше документ проходит ту же сверку, что и электронный.

| Этап | Как сделано | Файл |
|---|---|---|
| Проверка файла | тип определяется по содержимому (JPG, PNG, PDF), до 10 МБ, защита от «бомб декомпрессии», поворот по EXIF | `backend/app/ocr/loader.py` |
| Предобработка | OpenCV: масштаб, выравнивание наклона по линиям бланка, три варианта картинки — адаптивная бинаризация, канал для синих чернил, серое с локальным контрастом | `backend/app/ocr/preprocess.py` |
| Распознавание | Tesseract 5 (нейросеть LSTM), русский + английский, три варианта параллельно | `backend/app/ocr/engine.py` |
| Поля по шаблону | значение ищется рядом с подписью поля («Водитель», «Государственный номерной знак»…); варианты голосуют | `backend/app/ocr/template.py` |
| Проверка формата | госномер из 12 разрешённых букв, удостоверение, ФИО, даты; исправление 0/О, 3/З, I/1 только где формат однозначен | `backend/app/ocr/fields.py` |

Документы не покидают сервер банка: распознавание локальное, без внешних сервисов. Банк хранит оригинал файла, распознанные значения и то, какие поля человек исправил вручную. Если тот же файл приносят к другой заявке, оператор видит предупреждение. В пилоте вместо Tesseract можно подключить ABBYY или Yandex Vision за тем же интерфейсом.

**Образцы для показа** (`backend/samples/`):
- `ttn-1001-photo.jpg` и `trip-sheet-1001-scan.png` (или `.pdf`) — «чистая» пара: всё сходится, выплата проходит;
- `ttn-512.jpg` и `trip-sheet-329.jpg` — реальные бланки с расхождениями: другой водитель, машина, легковой путевой лист, нет медосмотра.

**Как показать:** перевозчик → заявка → блок «Документы рейса» → «Загрузить фото или скан» → проверить поля → «Подтвердить и подать».

Для запуска тестов модуля вне Docker нужен Tesseract с русским языком: `brew install tesseract tesseract-lang` на Mac.

## Архитектура

```
Десктоп (Tauri 2 + React)  ──HTTPS──▶  API (Python, FastAPI)  ──▶  PostgreSQL 16
три окна по ролям                      права → состояния → сверка    двойная запись,
токен только в памяти                  → леджер → лента решений      журналы только на добавление
```

Клиенту ничего не доверяем: деньги, правила и права живут только на сервере.

| Модуль | Файл | Что делает |
|---|---|---|
| Схема и защита в БД | `backend/migrations/001_init.sql` | Счета, проводки, заявки, документы, события, находки, лента, ключи идемпотентности |
| Леджер | `backend/app/ledger.py` | Проводки с двойной записью, проверка инвариантов |
| Сверка | `backend/app/reconcile.py` | Нормализация ФИО, госномеров, удостоверений; правила; простой |
| Бизнес-операции | `backend/app/services.py` | Машина состояний заявки, выплаты, споры, дубли, метрики |
| HTTP-слой | `backend/app/main.py` | Авторизация, идемпотентность, заголовки безопасности |
| Интерфейс | `frontend/src/` | Окна трёх ролей, симулятор, панель оператора |
| Оболочка | `frontend/src-tauri/` | Десктоп без доступа к ОС, строгий CSP |

## Безопасность

**Деньги:**
- Все суммы — целые копейки (`BIGINT`).
- Каждая проводка сходится в ноль; база проверяет это при COMMIT и откатывает несбалансированную транзакцию.
- Баланс счёта меняет только триггер проводки; прямой `UPDATE accounts SET balance` база отклоняет.
- Доступные деньги и резерв не могут уйти в минус: `CHECK` в БД.
- Проводки, лента решений и находки защищены триггерами от `UPDATE` и `DELETE`.

**Повторы и гонки:**
- `Idempotency-Key` на каждом действии пользователя; ключи одного пользователя сериализуются advisory-блокировкой.
- `event_id` у каждого события источника.
- `SELECT … FOR UPDATE` на заявку и счета (в порядке id, без взаимных блокировок).
- Номер накладной закрепляется за одной заявкой первичным ключом.

**Доступ:**
- Пароли — Argon2id; токены — 256 бит, в БД хранится только SHA-256, срок жизни 8 ч.
- Ограничение попыток входа; одинаковое время ответа для существующего и несуществующего логина.
- Роль и владелец заявки проверяются на сервере в каждой операции; чужая заявка отвечает 404, чтобы не раскрывать сам факт её существования.
- Строгая валидация входа: лишние поля запрещены, суммы и длины ограничены; запросы больше 64 КБ отклоняются.

**Десктоп:**
- Ни одного плагина Tauri и ни одной IPC-команды.
- CSP разрешает только свой код и API-сервер; `freezePrototype`.
- Токен хранится только в памяти окна.

**Контейнеры:**
- API не работает от root, файловая система только для чтения, все capabilities сброшены.
- Порт сервера опубликован только на `127.0.0.1`, база наружу не открыта.

**Для пилота:** TLS/mTLS между клиентом, сервером и адаптерами; подписи через КриптоПро (ГОСТ); секреты в хранилище банка; разграничение прав в PostgreSQL (отдельная роль приложения без TRUNCATE); журналирование в SIEM.

## Тесты

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
DATABASE_URL=postgresql+psycopg://user:pass@127.0.0.1:5432/escrow_test .venv/bin/pytest -q
```

43 теста на реальном PostgreSQL:
- сценарии 1–5 с точными суммами, нехватка средств, метрики, сброс данных;
- инвариант «деньги не появляются и не пропадают» после каждого сценария;
- права (заказчик не видит чужое, перевозчик не подтверждает стоимость, оператор видит всё);
- повторный ключ и повторное событие ничего не удваивают; 8 одновременных подтверждений дают одну выплату;
- база сама отклоняет несбалансированную проводку, прямую правку баланса, удаление из журналов и уход в минус;
- правила сверки на образцах ТТН №512 и путевого листа №329;
- распознавание: реальные фото и сканы бланков дают ожидаемые значения полей, PDF, права на загрузку, отказ на не-документах, повторный файл к другой заявке, полный путь «фото → подтверждение → сверка → выплата».
